🏠 1. Backend Overview

The BookWorm backend is a RESTful API server that powers a book-sharing / social app called BookWorm. It exposes authenticated endpoints for user registration, login, and CRUD operations on book posts (each post carries a title, caption, a 1–5 rating, and a cover image).

🎯 Main Purpose

Serve as the central data & business-logic layer: manage users, persist book recommendations, store cover images in the cloud, and secure all book operations behind JWT authentication.

🧱 Overall Architecture

A layered, monolithic Express server following a classic Routing → Middleware → Controller → (Service) → Model/Database pattern, with an internal cron worker and external integrations (Cloudinary, DiceBear, MongoDB Atlas).

🔁 Data Flow Summary

Client → Express Router → Auth Middleware → Controller → Mongoose Model → MongoDB Atlas. Cover images are uploaded to Cloudinary and referenced by URL; avatars are generated via the DiceBear API on registration.

Key characteristics

  • ES Modules — the package declares "type": "module"; the server runs from src/server.js.
  • Security — passwords hashed with bcryptjs (10 salt rounds) via a Mongoose pre-save hook; routes protected by a JWT protectRoute middleware.
  • Pagination — the books list endpoint supports ?page=&limit= for infinite-scroll loading.
  • Uptime keeper — a cron job self-pings the API every 14 minutes to keep it warm on free hosting tiers.

🔀 3. Request Flow

How a typical authenticated request (e.g. POST /api/books) travels through the backend:

sequenceDiagram
    autonumber
    participant Cl as Client
    participant Sr as Express Server

    participant Rt as /api/books Router
    participant Au as protectRoute (JWT)
    participant Co as Book Controller
    participant Cd as Cloudinary
    participant Db as MongoDB Atlas

    Cl->>Sr: POST /api/books (Bearer token + body)
    Sr->>Mw: parse JSON · enable CORS
    Mw->>Rt: forward request
    Rt->>Au: router.use(protectRoute)
    Au->>Au: verify JWT · load user (User.findById)
    Au-->>Au: attach req.user (401 if invalid)
    Au->>Co: next() → controller
    Co->>Cd: cloudinary.uploader.upload(image)
    Cd-->>Co: secure_url (cover image)
    Co->>Db: new Book({...}).save()
    Db-->>Co: saved document
    Co-->>Cl: 201 Created → JSON book

Notable source details

  • server.js is the single entry point — it starts the cron job, applies global middleware, mounts both routers, then connects the DB before app.listen.
  • The config/ layer centralizes infrastructure: DB connection, Cloudinary client, and the cron scheduler.
  • Controllers talk directly to Mongoose models (a separate service layer is not used).

🔌 6. API Architecture

Endpoints are grouped into two routers under /api. The books router is fully protected by the auth middleware via router.use(protectRoute).

Controllers & responsibilities

ControllerFunctionAction
auth.controllers.jsregisterAClientValidate fields → check duplicates → generate DiceBear avatar → hash+saved user → issue JWT (201)
auth.controllers.jsloginAClientFind by email → compare password → issue JWT (200)
books.controllers.jspostANewBookValidate → upload image to Cloudinary → save Book → 201
books.controllers.jsgetPaginatedBooksQuery with skip/limit, sort desc, populate user → paginated response
books.controllers.jsgetRecommendedBooksFetch books created by req.user (see note below)
books.controllers.jsdeleteABookOwnership check → destroy Cloudinary image → remove doc → 200

⚠️ Route shadowing caveat

In book.routes.js both getPaginatedBooks and getRecommendedBooks are registered on GET /. Express executes the first matching handler, so getRecommendedBooks is currently unreachable (shadowed). If intended, it should be mounted on a distinct path (e.g. GET /recommended).

🗄️ 8. Database Layer

MongoDB Atlas database bookworm_db contains two collections. The Book collection holds an ObjectId reference to a User (one user → many books).

erDiagram
    USER ||--o{ BOOK : "owns (ref: user)"
    USER {
        ObjectId _id PK
        string username "unique"
        string email "unique"
        string password "hashed"
        string profileImage "DiceBear URL"
        date createdAt "timestamps"
        date updatedAt "timestamps"
    }
    BOOK {
        ObjectId _id PK
        string title "required"
        string caption "required"
        string image "Cloudinary URL"
        number rating "1..5"
        ObjectId user FK "ref: User"
        date createdAt "timestamps"
        date updatedAt "timestamps"
    }

Collection / assignment summary

CollectionKey fieldsNotes
usersusername, email, password, profileImageUnique username + email; password auto-hashed in pre("save") hook
bookstitle, caption, image, rating (1–5), userPopulated with user's username & profileImage

Data flow

  • Write (books): Controller → upload cover to Cloudinary → build Book doc → save() → MongoDB.
  • Read (books): Controller → Book.find().sort().skip().limit().populate("user") → JSON payload with pagination metadata.
  • Write (users): Register controller → Mongoose pre-save hashes password → insert with profile image from DiceBear.
